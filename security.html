ZeroGuard DLP Security Architecture Statement

App version: 1.0.0
Audit hash version: 1
Platform: Atlassian Forge, nodejs24.x, 256 MB, arm64
Last reviewed: 21 October 2026

1. Executive summary

ZeroGuard DLP is a Forge-only app. It runs in Atlassian's cloud, uses Atlassian product APIs and Forge storage, and has no external egress or separate vendor backend. The app detects secrets and sensitive data in Jira issue summaries, ADF descriptions, and ADF comment bodies, masks the current field when policy is enforced, and writes a metadata-only audit record with HMAC integrity hashes.

The security design is built around four rules:

  1. Minimize data. The audit log never stores raw issue text, comment bodies, detected values, or full event payloads.
  2. Keep writes narrow. The app modifies only the current summary, description, or comment body that contained a finding.
  3. Make evidence verifiable. Each audit record has a domain-separated HMAC record hash and a separate outcome hash. Verification runs on the backend.
  4. Stay inside Atlassian. There is no external data plane, no dynamic webtrigger, and no third-party analytics or processing service.

2.2 Forge modules and scopes

The manifest declares:

  • jira:adminPage for the admin UI;
  • product triggers for issue create/update and comment events, both with ignoreSelf: true;
  • lifecycle triggers for install/upgrade and pre-uninstall;
  • a daily scheduled trigger;
  • a redaction-audit Custom Entity with by-time, by-project-time, by-status-time, by-project-status-time, by-event-status-time, and by-expiry indexes;
  • Forge licensing enabled; and
  • scopes read:jira-work, write:jira-work, and storage:app.

There is no permissions.egress, no external fetch, and no dynamic webtrigger.

3. Data flow

3.1 Detection and masking

  1. Jira delivers an issue or comment event to a Forge trigger.
  2. The app derives a stable event key from event-payload identifiers and timestamps. It does not use a random UUID or the fetched issue's updated value.
  3. The app checks licensing and policy. If scanning is disabled, the event is out of scope, or the license is inactive, the app exits without a Jira write.
  4. The app reads the issue/comment through the Jira REST API using asApp().
  5. The app scans:
    • summary text;
    • ADF description text nodes, link marks, and inline, block, and embed card URLs;
    • ADF comment body text nodes, link marks, and inline, block, and embed card URLs;
    • adjacent text nodes for values split by formatting.
  6. The app creates a PENDING audit record before any Jira write. The record contains metadata, findings, a snapshot hash, and HMAC hashes.
  7. The app re-reads the issue/comment twice to detect concurrent changes. It proceeds only after a stable snapshot.
  8. If the content is still unchanged at the final pre-write check, the app writes the masked current field with notifyUsers=false.
  9. The app completes the audit record with REDACTED, FAILED, or DETECTED (dry run) and an outcome hash.
  10. If the content changed, the app does not overwrite the newer user edit. It records a FAILED conflict outcome or reconciles a recovered clean state.

3.2 Audit lifecycle

PENDING ──► REDACTED   masked write succeeded
   │
   ├────► FAILED      write failed, conflict, missing field, or malformed scan
   │
   └────► DETECTED    dry-run finding

A record key is deterministic from the event key. If the same event key is seen again with a different raw snapshot, the app adds a snapshot-hash suffix so the older evidence is not overwritten. Retries of the same event/snapshot reuse the same key.

3.3 Read and write identity

  • Trigger reads and writes use asApp() because the app must operate independently of the user who triggered the event and must be able to mask content even after the user session ends.
  • The app requests only the Jira scopes it needs.
  • Project search in the admin resolver uses asUser() so Jira checks the administrator's project visibility.
  • The app does not use the browser UI to write Jira content.
  • notifyUsers=false is set on issue and comment updates.
  • ignoreSelf: true is set on both product triggers to reduce loops from the app's own writes.

4. Cryptographic design

4.1 Tenant salt

A 32-byte random salt is generated with Node's crypto.randomBytes and stored as 64 lowercase hexadecimal characters in Forge secret storage. It is created once per installation by the lifecycle handler and never returned to the admin UI.

The salt is the root secret for all HMACs in the installation. The app does not store it in audit records, logs, CSV exports, or resolver responses.

4.2 HMAC domains

All values use HMAC-SHA-256 with explicit domain separation:

Value Domain Output
Finding fingerprint zg:v1:fingerprint:<ruleId> 16 hex
Event key zg:v1:event 32 hex
Findings hash zg:v1:findings 32 hex
Record hash zg:v1:record 32 hex
Outcome hash zg:v1:outcome 32 hex

Domain separation prevents a fingerprint from being reused as an event key or audit hash even though all values use the same tenant salt.

4.3 Canonical JSON

Audit hashes are computed over a canonical JSON encoding with sorted object keys and JSON-safe scalar handling. The same encoding is used at creation and verification, so key order, undefined values, and nested object ordering do not create false mismatches.

4.4 Record and outcome integrity

The record hash covers the immutable creation evidence:

  • record type, record key, event key, event type;
  • issue ID, issue key, project ID, comment ID;
  • snapshot hash and findings hash;
  • finding count and truncation flag;
  • creation timestamp, app version, and hash version.

The record hash deliberately excludes status and completion fields, so a record can move from PENDING to REDACTED without invalidating its creation evidence.

The outcome hash covers:

  • the record hash;
  • status;
  • HTTP write status;
  • completion timestamp; and
  • the recovered flag.

The outcome hash includes the record hash so an outcome cannot be transplanted onto another record. Verification recomputes both hashes on the server and compares them with a timing-safe equality check after validating hexadecimal input.

4.5 What the audit log can and cannot prove

The audit log is tamper-evident. It can detect changes to a record that were not re-signed with the tenant salt. It is not:

  • an immutable ledger;
  • a public transparency log;
  • a global hash chain;
  • a trusted timestamp;
  • proof that Jira history was erased; or
  • proof that a masked value was never delivered to a webhook or notification.

A party with Forge app administration and access to both the audit storage and tenant salt could rewrite records and re-sign them. The design limits that risk through Forge access controls, backend-only secret access, and separation of the salt from the audit records, but it does not eliminate it.

5. Detection scope and write safety

5.1 Detected content

v1.0 scans:

  • issue summary;
  • ADF description text nodes, link mark URLs, and inline, block, and embed card URLs;
  • ADF comment body text nodes, link mark URLs, and inline, block, and embed card URLs.

The ADF walker preserves node structure where possible. It replaces sensitive text with placeholders, makes sensitive link/card URLs inert, and can collapse a value split across adjacent text nodes. It scans code blocks and formatted text.

It does not scan attachments, media nodes, arbitrary ADF attributes, custom fields, or Jira history. Those limitations are documented for customers.

5.2 Write guards

  • The app scans the current content immediately before writing.
  • It re-reads twice to establish a stable snapshot.
  • It compares the final pre-write snapshot with the audited snapshot.
  • If the content changed, it does not overwrite the newer content.
  • It uses deterministic event keys and audit status checks to avoid duplicate writes on retries.
  • It sets notifyUsers=false.
  • It uses ignoreSelf on triggers.
  • It records the actual Jira HTTP status instead of hardcoding a success code.
  • It creates the audit evidence before the write and completes the outcome afterward.

5.3 Known residual risk: Jira history

Masking the current field does not remove previous revisions. Jira may retain the original value in issue history, notifications, webhooks, indexes, backups, or integrations. Customers must rotate exposed credentials and use Jira administration controls for any additional erasure. The UI and documentation state this explicitly.

6. Administrative access and tenancy

  • The admin UI is a Forge jira:adminPage, available to Jira administrators.
  • Storage APIs are called only from backend functions and resolvers. The UI never receives the tenant salt.
  • Project search uses asUser() so Jira enforces the administrator's project permissions.
  • Policy updates store the updating account ID and timestamp.
  • Audit verification runs on the backend; the UI receives only per-record valid/invalid results.
  • Each Forge installation has isolated storage and its own salt. The app does not share audit records or policy across installations.
  • The resolver returns generic error messages to the UI and does not return raw Jira error bodies.

7. Logging and data minimization

The logger uses an allowlist. It can emit:

  • event name and level;
  • issue ID, issue key, project ID, comment ID;
  • event type;
  • status and HTTP status;
  • deleted/failed counts;
  • a bounded reason code;
  • app version; and
  • error class name.

It does not intentionally emit issue text, comment bodies, detected values, fingerprints, event keys, record keys, tenant salt, or full event payloads. Error messages from Jira are not logged because Jira error bodies can echo field values.

Audit records are also metadata-only. Findings store rule ID, 16-character fingerprint, location, and node type. The original value is discarded after the scan.

8. Licensing and lifecycle

  • Forge licensing is enabled in the manifest.
  • Backend trigger code checks context.license before scanning. If Forge explicitly reports the license as inactive, scanning pauses. An omitted license is treated as active so free-tier and development installations can scan; Atlassian remains responsible for Marketplace user-tier enforcement.
  • Retention runs even when unlicensed so data is still deleted on schedule.
  • The lifecycle handler ensures a tenant salt and default policy exist.
  • The pre-uninstall hook deletes up to 500 audit records and the policy on a best-effort basis. It intentionally leaves the salt so remaining hashes can verify during an interrupted uninstall. Forge removes app storage after uninstall under Atlassian's lifecycle.
  • Audit records have a TTL of up to 365 days; the daily job also deletes expired records.

8.1 Audit outcome and retry semantics

  • A scan creates a PENDING record before any Jira write. If the audit record cannot be created, the app does not write to Jira.
  • A successful Jira write becomes REDACTED only when the conditional audit update succeeds. The scanner compares the returned terminal status and logs audit-incomplete when another invocation or a storage conflict produced a different result; it does not claim success from the Jira response alone.
  • A FAILED record is terminal evidence. The same Forge delivery is not retried indefinitely after a non-retryable Jira error or a content conflict; a later user edit creates a new event key and a new scan. Transient storage failures remain retryable and are surfaced to Forge.
  • When a retry finds the content already clean, the app reconciles a prior PENDING record to REDACTED with recovered=true. A deleted or expired record is not recreated or resurrected. “Clean” means no finding under the rules enabled at retry time; if an administrator has since disabled a rule, the earlier finding is preserved as evidence but is not re-proven masked.
  • If the same event key is seen with a different raw snapshot, the new record uses a snapshot suffix so the earlier evidence is preserved.
  • The completion write is a conditional transaction on recordHash and status === 'PENDING' when Forge supports it. This narrows the race between concurrent invocations; it is not a substitute for the Jira pre-write snapshot check.
  • Storage errors are classified as retryable or non-retryable. Schema and permission errors stop the retry loop instead of producing an infinite Forge retry; transport and 5xx errors are retried.
  • Each audit record carries its signed expiry. The daily job deletes records whose expiry has passed and records older than the current retention setting, so increasing retention does not extend older evidence and decreasing it applies the shorter window. A failed deletion batch is retried on the next run. If one retention index query is unavailable, the other cleanup source still runs and the job reports partial rather than deleting nothing.

8.2 Coverage and lifecycle limits

  • ADF coverage includes text nodes, code blocks, link URLs, link titles, expand titles, status text, and inline/block/embed card URLs. Cross-node detection is bounded to runs of 8 adjacent text nodes and 4,000 characters. Media nodes, attachment contents, custom fields, and arbitrary ADF attributes are out of scope for v1.0.
  • The app does not backfill pre-existing issues or comments. It scans content delivered by Jira create/update events after installation.
  • An omitted context.license is treated as active for free, development, and non-production contexts so the app remains usable when Forge does not supply a license object. The app pauses only when Forge explicitly reports an inactive license.
  • Pre-uninstall cleanup is best-effort and deletes up to 500 audit records plus the policy. It intentionally keeps the tenant salt so remaining hashes can verify during an interrupted uninstall; TTL and platform cleanup remain the backstop.

9. Egress and data residency

The app makes requests only to Atlassian Jira REST APIs and Forge storage/services. It does not call an external endpoint, use a dynamic webtrigger, load third-party scripts, or send telemetry to the vendor.

This architecture is intended to support Atlassian's "Runs on Atlassian" program and inherited Forge data residency. Final eligibility is determined by Atlassian's review of the submitted app and listing. The app does not make an independent data-residency promise outside Atlassian's Forge capabilities.

10. Threat model

Threat Control Residual risk
Raw secret appears in app logs Metadata allowlist; no error bodies; no raw findings in logs. Platform-level logs or a future code regression; covered by review and tests.
Raw secret stored in audit Audit model stores only rule ID, fingerprint, location, node type, identifiers, and hashes. Fingerprints permit correlation.
Duplicate writes / update loop ignoreSelf, deterministic event keys, audit status checks, idempotent writes. Forge may redeliver events; content is re-scanned and clean scans do not write.
Concurrent audit completion Conditional transaction on recordHash and PENDING; terminal record re-read before write. If transaction conditions are unavailable or change, the record may remain PENDING and retry until reconciliation.
False success claim Scanner logs success only when the audit terminal status matches the Jira outcome. Storage can fail after Jira succeeds; the scanner retries and then reconciles from the clean content.
Concurrent user edit overwritten Two re-reads; final snapshot comparison; conflict FAILED/recovered outcome. A change can land after the final read and before the write.
App writes with admin privileges Scopes limited to Jira work and app storage; writes only masked current fields; no arbitrary field updates. A compromised app deployment could use its scopes; protect the Forge app and vendor account.
Unauthorized admin access Jira admin page; backend-only storage; asUser() project search; account ID recorded on policy save; mypermissions check before policy saves and audit purges. A Jira administrator can purge audit records by design.
Audit tampering HMAC record/outcome hashes; salt in secret storage; backend verification; timing-safe compare. Storage + salt administrator could re-sign; no external anchor.
Cross-tenant leakage Forge installation isolation; per-install salt; no shared backend. Platform isolation depends on Atlassian.
CSV formula injection Leading whitespace followed by = + - @ tab CR neutralized; every cell quoted. Spreadsheet behavior varies; export remains metadata-only.

False negative in unsupported ADF shapes Strings and bare content arrays are normalized; cards, link titles, expand titles, and status text are covered. Media/attachment contents, custom fields, and arbitrary attributes are not scanned in v1.0.

Data left after uninstall TTL, daily retention, best-effort pre-uninstall cleanup. Pre-uninstall is time-limited and non-blocking; platform cleanup is outside app control.
Pre-existing sensitive content Event-driven scanning covers new and edited content; limitations are documented in the app and README. No automatic backfill in v1.0; install does not scan historical issues.
Comment edit not delivered Jira's comment event is documented as create-and-edit; app re-reads comment and determines created vs updated. Validate in the target Jira site; see validation spikes.

12. Incident response

If a vulnerability or suspected data exposure is reported:

  1. Acknowledge the report at joel.revuel@gmail.com and establish a private channel.
  2. Preserve metadata-only evidence. Do not request raw secrets or issue bodies.
  3. Assess the affected app version, installation scope, and whether the tenant salt or audit storage could be accessed.
  4. Contain the issue through a Forge deployment rollback or fix; coordinate with Atlassian if the platform is involved.
  5. Notify affected customers and Atlassian as required by law and Marketplace policy.
  6. Rotate any credential that may have been exposed; masking does not remove prior history or notifications.
  7. Document the root cause, fix, and verification, and update tests and this statement.
