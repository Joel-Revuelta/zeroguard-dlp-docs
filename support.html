2. Support scope

We provide support for:

  • installation and licensing questions;
  • configuration of policy scope, rules, dry-run mode, and retention;
  • unexpected trigger, resolver, or audit behavior;
  • audit integrity verification questions;
  • CSV export and fallback behavior;
  • suspected security issues in the app; and
  • compatibility questions for supported Jira Cloud/JSM environments.

We do not provide:

  • Jira administration, Jira history rewriting, or Atlassian platform support;
  • recovery of a credential that was exposed (rotate it immediately);
  • legal, compliance, or data-protection advice;
  • custom development, unless separately agreed in writing;
  • support for modified app code or unsupported Forge runtimes; or
  • guarantees that every secret or sensitive value will be detected.

For Atlassian platform incidents, use Atlassian Support. For Jira permission, notification, webhook, backup, or history questions, contact the Customer's Jira administrators or Atlassian.

3. Response targets

These are targets, not a guaranteed service-level agreement unless a separate written agreement says otherwise:

Severity Definition Target first response
Security / critical Suspected vulnerability, data exposure, or complete loss of masking in a production site. Within one business day
High Scanning, writeback, licensing, or audit integrity is unavailable for a production site; no workaround known. Within two business days
Normal Configuration question, isolated failure, documentation issue, or reproducible bug with a workaround. Within three business days
Low Feature request, cosmetic issue, or general question. Within five business days

Business days exclude weekends and public holidays at the vendor's location. Response time is not resolution time. We may ask for reproduction steps, timestamps, and metadata-only diagnostics.

4. What to include in a support request

Please include:

  • Jira site URL and cloud ID, if known;
  • Jira or JSM product and approximate user tier;
  • app version (shown in the admin page footer or bootstrap response);
  • the approximate event time in UTC, including time zone;
  • issue key or issue ID, and comment ID if relevant;
  • event type (issue created, issue updated, comment created, comment edited);
  • the audit status (PENDING, REDACTED, FAILED, or DETECTED) and any httpStatus;
  • whether dry-run or enforcement was active;
  • policy scope mode and the relevant project ID;
  • the exact error text shown in the UI, if any; and
  • steps to reproduce with fake test data.

Do not include:

  • live API keys, passwords, private keys, or tokens;
  • raw issue summaries, descriptions, or comment bodies;
  • screenshots containing secrets;
  • full event payloads;
  • tenant salt values; or
  • personal data that is not necessary for the request.

If a screenshot is essential, redact the sensitive value and preserve only the surrounding layout and error text.

5. Security vulnerability reporting

Please report security issues privately to joel.revuel@gmail.com. If possible, include:

  • a description of the issue and affected version;
  • the security impact and attack prerequisites;
  • reproduction steps using a test installation or fake data;
  • whether the issue affects confidentiality, integrity, availability, licensing, or tenant isolation; and
  • any suggested remediation.

We will:

  1. acknowledge the report and establish a private channel;
  2. validate and triage the issue;
  3. develop and test a fix;
  4. coordinate disclosure with the reporter and, where relevant, Atlassian; and
  5. credit the reporter if they wish and if coordinated disclosure permits.

Please give us a reasonable opportunity to fix the issue before public disclosure. Do not access, modify, or exfiltrate another customer's data, disrupt a production site, or use social engineering.

6. Diagnostic data and privacy

The app is designed to log metadata only. When requesting diagnostics, we will ask for the smallest set of metadata needed to reproduce the issue. Do not send secrets. If a log line appears to contain sensitive data, stop and report it as a security issue rather than forwarding it.

Support communications may be retained for as long as needed to resolve the request, meet legal obligations, and improve the app. See the Privacy Policy for the app's data handling.

7. Supported versions

We support the current Marketplace release and the immediately preceding minor release for security fixes, where practical. Jira Cloud is continuously updated; we may not be able to support an app version after Atlassian changes a required API or runtime.

The v1.0 app targets Forge nodejs24.x. Unsupported runtimes, modified code, or self-hosted deployments are outside support.

8. Escalation

If a request is not progressing or involves a suspected security incident, reply to the existing support thread with "ESCALATE — security" or email joel.revuel@gmail.com with the original thread reference. Include the site URL, app version, and a concise impact statement. Do not include secrets.

9. Status and changes

We may update this policy as the app, support process, or Marketplace requirements change. The updated version will show a new effective date. Material changes will be noted in the Marketplace listing or documentation where appropriate.
